## Design decisions

- `src/` layout: tests import the installed package, so packaging bugs show up early.
- mypy `strict` from day one: cheaper than retrofitting types later.
- GPU tests use a `gpu` marker and auto-skip without CUDA: one suite for laptop, CI and Kaggle.
- pre-commit hooks are `local`: they reuse the venv's ruff/mypy, so local and CI versions never drift.
- `.gitattributes` forces LF: development is on Windows, CI is Linux; avoids whole-file CRLF diffs.
- CI tests 3.11, 3.12 and 3.14: Kaggle/Colab run 3.11-3.12, the laptop runs 3.14.
- CI matrix `fail-fast: false`: one red version should not hide the others' results.
- `xfail_strict = true`: a test marked xfail that starts passing fails the run, so stale xfail markers can't hide fixed or changed behaviour.
- Unsupported config features (bias, rope_scaling, non-SiLU) are rejected, not ignored: fail at load, not mid-generation.
- `head_dim` is read from config, never derived: Qwen3-0.6B uses 16 heads x 128 = 2048, not hidden_size 1024.
- No `transformers` at runtime: config.json is plain JSON, read with the standard library. huggingface_hub is only the download client.
- Weights default to fp16: Turing tensor cores do fp16, not bf16. bf16->fp16 can overflow, so the loader checks for inf/nan.
- Strict loader (missing, unexpected or misshapen tensor = error): a silent mismatch would surface much later as wrong tokens.
- RMSNorm and RoPE do their math in fp32 and cast back: fp16 squares overflow past 255, and RoPE angles reach 40960 rad.
- RoPE uses the rotate-half layout (pair i with i + D/2): it is what Qwen3 was trained with; interleaved pairs give wrong tokens.
- RoPE takes explicit positions per token: in a continuous batch every sequence is at a different position.
- Linear layers use `F.linear(x, w)` on the checkpoint's [out, in] weights: no transposed copies, so memory stays at 1x.
- Reference attention is plain PyTorch (einsum + mask + softmax in fp32): the paged cache (M2) and Triton kernel (M4) are tested against it.
- GQA maps query head h to kv head h // (Hq/Hkv) (`repeat_interleave`, not `repeat`): that is how Qwen3 groups heads.
- M1 has no KV cache: each step re-runs the whole sequence (O(n^2)). Simplest correct baseline; M2 replaces it.
- Qwen3 applies q_norm/k_norm per head before RoPE; the output head reuses the embedding matrix (tied).
- M1 acceptance is measured in fp32 on CPU: it isolates algorithm bugs from fp16 kernel rounding, which is a separate question for the GPU milestones.
- `transformers` is a dev-only dependency used as the reference in tests; tinyserve never imports it.
- CI installs CPU-only torch: no GPU there, and the default Linux wheel pulls ~3 GB of CUDA libraries.
- Block allocator is plain Python with no tensors: bookkeeping is separate from the KV memory, so it can be property-tested in milliseconds.
- Free blocks are a list used as a stack: allocate and free are O(1) per block, and a just-freed block is reused first.
- Used blocks are tracked in a set: the double-free check is O(1) instead of scanning the free list.
- allocate() and free() are all-or-nothing: on an error nothing changes, so the M3 scheduler can catch OutOfBlocksError and preempt safely.
- Slot of position p = blocks[p // block_size] * block_size + p % block_size: the KV cache is addressed as one flat array of token slots, so writes in step 3 are a single scatter.
- A block table never holds an empty block (blocks = ceil(tokens / block_size)): blocks are only taken when a token needs one.
- KV cache stored per layer as flat token slots [num_slots, Hkv, D]: writing new tokens is one indexed assignment, and the same memory viewed as [num_blocks, block_size, Hkv, D] is the block layout the M4 kernel reads.
- Paged attention takes the query positions as the LAST n of the sequence: one function covers prefill (n = total), decode (n = 1) and chunked prefill.
- Paged attention gathers k/v into a contiguous copy before the math: slow, but obviously equal to the M1 reference. M4's kernel reads blocks in place instead.
- The KV cache stores fp16 by default (fp32 on CPU in tests): it is the largest memory user after the weights.
- The model has one layer stack and takes attention as a function: the no-cache path (M1) and the paged path share every other line, so they cannot drift apart.
- `greedy_generate_paged` releases the sequence's blocks in a `finally`: an error mid-generation cannot leak cache memory.
- Batched forward flattens new tokens with no padding (sequence after sequence, `[T]`): linear layers and the MLP run on all rows at once and no compute goes to padding; only attention splits by sequence.
- `forward_batch` computes the output head only for each sequence's last new token: the 151,936 x 1,024 head is the largest matmul, and the other prefill rows are never sampled.
- All new tokens' k/v are written to the cache in one scatter per layer before attention: a sequence only ever reads its own slots, so writing everyone's first is safe.
- Scheduler re-plans before every step (continuous batching, Orca): finished sequences leave and waiting ones join at once, instead of a static batch waiting for its slowest member.
- Running sequences get their next slot before any new sequence is admitted: work already in progress is never starved by new arrivals.
- Preemption evicts the newest running sequence: the oldest always keeps its blocks, so it always makes progress and preemption cannot livelock.
- Preemption by recompute (free the blocks, re-run prompt + output as one prefill), not swapping k/v to CPU: no extra memory or copy path; the cost is repeated prefill work.
- A preempted sequence goes to the front of the waiting queue: it arrived before everything behind it.
- Admission is strict FCFS and stops at the first request that doesn't fit: no skipping ahead, so long requests are not starved by short ones.
- Requests whose longest possible length exceeds the batch token budget or the whole cache are rejected at `add()`: after a preemption they could never be re-admitted.
- The engine records one timestamp per output token, not just per request: TTFT, TPOT and their percentiles all come from the same raw data.
- The engine's clock is injectable: timing tests use a fake counter instead of sleeping or asserting on real time.
- Benchmark is closed-loop at a fixed concurrency (a new request as soon as one finishes): concurrency is then a controlled variable, matching the M3 criteria (1/8/32/64).
- Benchmark requests ignore EOS and all produce exactly `--output-len` tokens: runs at different concurrencies (and against HF) do the same work.
- Benchmark prompts are random token ids from a fixed seed: the work per request is exact and reproducible; the text content does not change the cost of a forward pass.
- TPOT is averaged per request first, then p50/p99 are taken across requests: one number per request, so long requests don't dominate the percentiles.
- HF baseline is static batching (batches of C run to completion) with the same prompts and fixed output length: that is what `generate()` offers, and identical inputs make the throughput comparison fair. Only tok/s is compared; HF's per-token times are not observable.
- Requests per benchmark level scale with concurrency (4 per slot, at least 16): concurrency 64 runs several waves, and concurrency 1 does not take an hour.
- Device bugs are caught on CPU by running the model on the `meta` device: it has no data, but it refuses to mix with CPU tensors, so any tensor created without `device=` fails a laptop test instead of a GPU run.
- Attention's cost is measured by replacing it with a stand-in (returns q) and timing the difference: a direct ablation is easier to trust than adding up profiler rows, and it includes the Python launch overhead the profiler splits across many ops.
- The decode kernel runs one program per (sequence, query head) and loops over that sequence's blocks: no padding work for short sequences, and the block table is read in place, so there is no gather copy. Sharing each loaded k/v block between the 2 query heads of a GQA group is a later optimisation, to be measured.
- Online softmax (running max, sum and weighted sum, rescaled when the max grows): one pass over the blocks with O(D) state per program, and no overflow because exp() only ever sees score - max <= 0.
- The kernel takes block ids (`[B, max_blocks]` int32) and lengths, not per-token slots: one int per block instead of one per token, and slot = block * block_size + offset is computed in the kernel.
- Kernel tests fill every slot no sequence owns with NaN: any out-of-range read shows up as NaN instead of passing by luck on zeros.
- Without a GPU, kernel tests run in Triton's interpreter (`TRITON_INTERPRET=1`, set in conftest.py): CI checks the kernel's results on CPU. Triton has no Windows wheels, so on the laptop these tests skip.
- The kernel is opt-in (`decode_attention="triton"`), not automatic on CUDA: the PyTorch path stays the reference, and the benchmark records which path produced each number.
- Mixed batches split by sequence: one-token sequences go to the kernel, longer ones (prefill) to the PyTorch path, and both write into one output tensor by row; prefill is a minority of steps at steady state.
- fp16 greedy parity on the T4 is judged against the same check without the kernel, not against zero: fp16 rounding flips near-ties (margins of 0 to 1 fp16 step) in both paths, so the kernel is accepted if it adds only near-tie flips. Exact parity is measured in fp32.
- M2 starts without reference counts; the M5 prefix cache, where sequences share blocks, will add them.
- M5: reference counts live in the block allocator (`share` / `free`), not in the prefix cache: the allocator is the one place that decides when a block is really free, so a sequence, the cache, or both can hold a block and it returns to the pool exactly when the last one lets go (vLLM v1 also keeps `ref_cnt` per block).
- M5: only full blocks are shared, never a sequence's partly filled last block: a sequence only writes past its last token, so shared blocks are never written and no copy-on-write is needed.
- M5: the tree is block-granular (keys compared one block of `block_size` tokens at a time, children keyed by their first block): a match can only end on a block boundary, so matched tokens map to whole blocks with no partial-block bookkeeping.
- M5: a match that ends inside a node splits it there: every node is then used by a sequence entirely or not at all, so eviction can decide per node.
- M5: eviction is LRU over leaves whose blocks have reference count 1 (only the cache holds them), one heap per `evict` call: a block a running sequence reads is never freed, and removing leaves first keeps every cached path connected to the root. LRU time is a counter, not the wall clock, so tests are deterministic.
- M5: admission never reuses a prompt's last token, even when it is cached: that token's logits pick the first output token, so at least one token is always run. With whole blocks only, an 8-token prompt in blocks of 4 reuses 4 tokens, not 7.
- M5: finished AND preempted sequences are cached (prompt and generated tokens, whole blocks): a follow-up request that repeats a chat history hits it, and a preempted sequence's recompute reuses whatever of its blocks survives eviction.
- M5: evict cached blocks before preempting anyone, and LRU picks the victim among cached blocks: evicting a cached block costs a possible future recompute, preempting a running sequence costs a certain one.
- M5: blocks are cached right after a prefill as well as at finish: a long shared prompt is reused by requests that arrive while its first user is still decoding (SGLang also caches unfinished requests). Prompt blocks are full and never written again, so sharing them with a running sequence is safe.
- M5: the prefix cache is opt-in (`prefix_cache=True`), like the kernel: earlier results stay reproducible, and every result records whether the cache was on.
- M5: whole leaves are evicted, so `evict(n)` can free a few more blocks than asked: simpler than splitting a leaf, and the extra blocks were the least recently used ones anyway.
- M6: sampling uses the exponential race (argmax of p / E with E ~ Exp(1)) instead of `torch.multinomial`: it is exact, needs no renormalisation after top-p (dropped tokens have p = 0), and is one elementwise op plus one argmax for the whole batch (vLLM samples the same way).
- M6: temperature 0 means greedy and is the default, and an all-greedy batch skips softmax and noise entirely: greedy parity with HF stays exactly the M1-M5 code path.
- M6: a request with a seed gets its own generator, so its tokens depend only on its prompt, parameters and seed, not on the batch it lands in (continuous batching changes the batch every step); requests without a seed share one engine generator.
- M6: one engine thread, many asyncio clients, connected by a command queue (in) and per-request asyncio queues (out): the engine stays single-threaded, so the scheduler, allocator and caches need no locks, and requests join or leave exactly between steps, where continuous batching already re-plans.
- M6: a disconnected client's request is aborted at once and its blocks freed (its full blocks cached first): a dropped connection must not keep using cache and batch slots until max_tokens.
- M6: detokenise incrementally over a short window that starts on a character boundary, and hold back pieces ending in U+FFFD: token-by-token decoding breaks multi-byte characters, and decoding the whole output every step is O(n^2).
- M6: the API waits for a request's first output before it starts the HTTP response: a request the engine refuses (or a full queue) gets a real status code (400 / 429) instead of a 200 stream with an error inside.
- M6: OpenAI-compatible defaults (temperature 1.0) even though the engine's default is greedy: clients written for OpenAI get the behaviour they expect; temperature 0 gives exact greedy parity.
- M6: unbuilt OpenAI features (n > 1, stop, logprobs, echo, penalties) are refused with 400, not silently ignored: a client must not get an answer computed differently from what it asked for.
- M6: bind to 127.0.0.1 by default, and refuse other hosts without `--allow-remote`: there is no authentication, so exposing the port means anyone who can reach it can use the GPU.
- M6: the API benchmark runs the M3/M4 workload unchanged (same prompts, EOS ignored) and the engine-only benchmark in the same session: the difference is what HTTP, JSON, SSE and detokenising cost, not a different workload.
- M6: greedy parity through the API compares text (HF's tokens decoded with the same tokenizer) with token-id prompts: the API returns text, and token-id prompts keep tokenisation out of the comparison.

M3 T4 analysis (written at M3 from the numbers alone; M4 step 1 then confirmed it with the profiler):
- TinyServe / HF throughput: 1.01x at C=1, 0.37x at C=8, 0.21x at C=32, 0.20x at C=64. The target (>= 3x HF at C=32) is not met.
- Our TPOT grows almost linearly with the batch: 39, 113, 363, 708 ms at C=1, 8, 32, 64, i.e. about 11 ms per extra sequence per step. HF's batch time grows far more slowly. The likely cause is attention: `forward_batch` calls `paged_gqa_attention` once per sequence per layer (28 x C calls per step), and each call gathers and copies that sequence's k/v. The batched linear layers and MLP should cost little extra per sequence. This is what the M4 Triton kernel replaces with one launch per layer.
- TTFT p99 at C=64 (2.1 s) is queueing: with a 2,048-token step budget, only about 15 new 128-token prompts fit in one step, and each step already takes ~0.7 s.

M4 T4 analysis (from the M4 step 1 and step 3 profiles):
- The kernel removed the per-sequence attention cost: kernel launches per C=64 forward fell from 30,603 to 1,962, and the forward from 740 ms to 40 ms. TPOT now grows from 34.8 ms (C=1) to 52.5 ms (C=64) instead of 39 to 708 ms.
- TinyServe / HF throughput: 1.14x, 1.12x, 1.72x, 2.59x at C = 1, 8, 32, 64. The >= 3x target at C=32 is not met.
- What limits C=32 now: a decode forward is ~34 ms at C = 1, 8 and 32 alike, so the step is a fixed cost, not attention. With the kernel the GPU is busy only 44% of a C=64 forward; most of the remaining 1,934 launches per step are small linear, norm and RoPE kernels, each launched from Python. At C=32 the engine also spends ~8 ms per step outside the forward (TPOT 42.4 ms vs forward 34.3 ms): `build_batch` (4.1 ms, per-token Python lists), scheduling, and the `argmax().tolist()` sync. The likely next wins are CUDA graphs for the decode step (a stretch goal) and building the batch without per-token Python work. Measure before choosing.
- TTFT p99 at C=64 (1.3 s) is prefill queueing: prompts still attend one sequence at a time in PyTorch, and at most ~15 new 128-token prompts fit in one 2,048-token step.

M5 T4 analysis (shared-prefix workload: 4 prefixes of 1,024 tokens, 64-token suffixes, 64 output tokens; numbers from the run, causes marked where inferred):
- Hit rates are exactly (N - 4) x 1,024 / (N x 1,088) at every level (70.6% / 82.4% / 91.2% for N = 16 / 32 / 128): only the first request of each prefix missed. That needs blocks cached right after prefill (step 4); with caching at finish only, the whole first wave at C=32 would have missed.
- C=1: median TTFT 232 -> 42 ms (5.5x): a hit prefills 64 tokens instead of 1,088. p99 is unchanged (234 / 236 ms) because 4 of the 16 requests are those misses. TPOT is the same (33 ms), as expected: decode does not change.
- C=8: TTFT p50 266 -> 111 ms, p99 1,944 -> 1,138 ms; throughput 121 -> 188 tok/s (1.55x); TPOT 61.7 -> 37.9 ms. Inferred: without the cache, a 1,088-token prefill is in most steps and slows every decode that shares the step.
- C=32: throughput 149 -> 335 tok/s (2.24x), TTFT p99 8.9 -> 2.0 s (4.5x), TPOT 207 -> 82 ms, KV utilization mean 87% -> 34% (shared blocks). Median TTFT got worse, 346 -> 704 ms. Inferred, not profiled: without the cache only one 1,088-token prompt fits in a 2,048-token step, so the first wave queues for up to 32 steps (the p99) but later arrivals are staggered and wait about one step. With the cache ~30 hits fit in one step, so the closed loop runs in synchronized waves: ~30 requests arrive together, and their first token waits for one step that prefills all of them, each attending over 1,088 cached tokens one sequence at a time in PyTorch (the prefill path the M4 kernel does not cover).
- fp16 outputs with the cache on vs off: identical for 16/16, 32/32 and 124/128 requests. fp32 greedy parity with the cache (24 chat prompts sharing a system prompt, 76.5% of prompt tokens from the cache): 0 mismatches / 384 tokens. The 4 fp16 differences are probably near-ties (a cached prefix changes the prefill's matmul shapes), but that is not verified.

M6 T4 analysis (the engine alone and the same workload over HTTP in one session; HF from the M3 run; causes marked where inferred):
- Throughput over HTTP: 30.0 / 221.7 / 723.8 / 1,124.0 tok/s at C = 1 / 8 / 32 / 64, vs 30.7 / 231.1 / 766.4 / 1,205.9 for the engine alone in the same session: HTTP, JSON, SSE and detokenising cost 2.3% / 4.1% / 5.6% / 6.8%. Against HF `generate()` (M3 session): 1.19x / 1.15x / 1.74x / 2.49x through the API; the engine alone is at 1.84x / 2.67x at C = 32 / 64. The >= 3x target at C=32 is still not met.
- TPOT over HTTP is 0.7-1.8 ms above the engine's (33.2 vs 32.4 ms at C=1, 52.2 vs 50.4 ms at C=64): the per-token cost of sending an SSE chunk is small.
- TTFT is where HTTP costs most, and it grows with concurrency: median +3 / +82 / +183 / +341 ms at C = 1 / 8 / 32 / 64, p99 5.6 s vs 0.6 s at C=32 and 7.3 s vs 1.2 s at C=64. Inferred, not profiled: the engine thread and the event loop (request parsing, JSON, SSE for every stream) share one Python interpreter, so the event loop gets the GIL only between the engine's Python work, and the benchmark client competes for the same 2 CPU cores. A new request's "add" can then reach the engine thread several steps late. Profiling the server under load (M7) should confirm or refute this before anything is changed.

## Open questions

- API TTFT under load (p99 5.6 s at C=32 vs 0.6 s for the engine alone): profile the server to confirm the inferred GIL contention between the engine thread and the event loop; candidate fixes are fewer Python steps per token (CUDA graphs) or moving HTTP to its own process.
- C=32 median TTFT with the prefix cache (704 ms vs 346 ms without; fp32 943 vs 585 ms): confirm the inferred cause with per-step timings; batched prefill attention over cached blocks (or a cap on new prefills per step) would be the fix to measure.

- Resolved 2026-10-18 (M6 step 4): the 4 / 128 fp16 output differences with the prefix cache were rounding: in fp32, 128 / 128 identical.
